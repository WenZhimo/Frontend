# 磷光矩阵视觉验证项目报告

本文档整理本项目从参考图视觉定义，到技术规格拆解，再到最终滤镜实现与优化的完整过程。

项目目标不是构建一个完整产品，而是验证一种特定视觉语言是否可以在普通网页环境中被实现：让普通网页内容经过处理后，呈现为冷蓝白磷光矩阵显示，接近参考图中“被摄影机拍摄到的物理发光阵列”。

## 1. 项目背景

本项目起点是一组参考图。参考图的视觉特征非常明确：

- 黑暗背景中的冷蓝白发光信息
- 密集、规则、可见的矩阵单元
- 每个单元独立发光
- 高亮区域有白蓝核心
- 外围有蓝紫色柔和光晕
- bloom 不应吞掉矩阵结构
- 画面像真实物理显示器被拍摄，而不是普通网页特效

因此，本项目从一开始就避免把目标理解为常见的“CRT 滤镜”“VHS 故障”“绿色终端”“霓虹发光字”或“CSS glow”。这些方向虽然常见，但都不符合参考图。

## 2. 第一阶段：视觉反向工程

第一阶段的工作是从参考图中提炼视觉规范，输出为：

- `磷光矩阵视觉规范.md`

这份文档定义了整个项目的视觉真相。其核心判断是：

该视觉不是复古屏幕效果，而是冷蓝白磷光矩阵显示。画面中所有发光信息都应来自独立发光单元。文字、波形、线条和高亮区域都必须被矩阵采样。即使在最亮区域，仍应能看到格点和暗缝。

### 关键视觉原则

视觉优先级被确定为：

1. 独立发光单元
2. 可见矩阵结构
3. 冷蓝白磷光
4. 白热核心与蓝紫外晕
5. 摄影式柔焦与暗部扩散
6. 高黑位对比
7. 科学仪器式克制排版
8. 轻微低光摄影噪声
9. 无故障、无娱乐化装饰

其中前四项不可牺牲。如果没有独立发光单元、矩阵结构、冷蓝白色彩和高光穿透矩阵，画面就不再符合参考图。

### 明确排除的方向

视觉规范明确排除了：

- CRT 曲面和桶形畸变
- RGB 分离和彩边
- VHS 雪花、撕裂和磁带拖影
- 绿色终端
- 多色赛博朋克霓虹
- 平滑矢量发光字
- 普通对象外描边 glow

这个负面清单很重要。它防止后续实现为了“像屏幕效果”而滑向错误风格。

## 3. 第二阶段：实施规格设计

第二阶段将视觉规范转化为技术实施规格，输出为：

- `磷光矩阵技术实施规格.md`

这个阶段分析了当前项目结构：

- 单文件静态网页
- 原生 HTML/CSS/JavaScript
- 内联 CSS
- 多个 DOM 区块
- Canvas 2D 动画
- Chart.js 图表
- 视频、图片、SVG
- 一个预留的全屏 canvas 覆盖层 `shaderMount`

项目没有构建系统，也没有框架。因此实现方案必须适合无构建、浏览器直接运行的环境。

### 架构判断

实施规格比较了几种路线：

| 路线 | 结论 |
| --- | --- |
| 纯 CSS | 无法实现单元级矩阵和真实 bloom |
| CSS + SVG | 不适合覆盖动态网页内容 |
| Canvas 2D | 可作为原型和 fallback |
| WebGL 后处理 | 适合高保真矩阵、发光、bloom 和合成 |
| Hybrid rendering | 最终选择 |

最终选定的是混合架构：

- DOM 保留为真实内容、布局、语义和交互层
- 视觉效果由 `shaderMount` 覆盖层承载
- 覆盖层保持 `aria-hidden="true"` 和 `pointer-events: none`
- 渲染器负责把页面视觉输入转化为磷光矩阵

这种结构能保证视觉层不破坏页面可访问性和交互。

## 4. 第三阶段：Canvas 2D 原型实现

第一版实现采用 Canvas 2D，目标是先跑通完整物理阶段，而不是马上追求最高性能。

实现新增了独立渲染库目录：

- `phosphor/renderer/config.js`
- `phosphor/renderer/display-surface.js`
- `phosphor/renderer/source-sampler.js`
- `phosphor/renderer/pixel-matrix.js`
- `phosphor/renderer/emission.js`
- `phosphor/renderer/bloom.js`
- `phosphor/renderer/lens.js`
- `phosphor/renderer/texture.js`
- `phosphor/renderer/phosphor-pipeline.js`
- `phosphor/renderer/phosphor-renderer.js`

Demo 接入放在：

- `test/phosphor-demo.js`

测试页 `index.html` 只负责加载 demo、放置控制项和提供 `shaderMount`，没有把渲染逻辑塞回页面内部。

### Canvas 2D 管线

Canvas 原型管线为：

```text
页面内容
→ SourceSampler
→ PixelMatrix
→ EmissionRenderer
→ BloomRenderer
→ LensDiffusion
→ DisplayTexture
→ shaderMount
```

### Canvas 原型解决了什么

它验证了：

- 普通网页内容可以被转译成磷光矩阵视觉
- 文字、面板、图表、图片、canvas 都可以进入同一套矩阵系统
- 单元级发光、白蓝核心、蓝紫外晕可以在浏览器中近似实现
- 覆盖层不会阻断原页面交互

### Canvas 原型的问题

它也暴露了明显问题：

- CPU 逐点绘制成本高
- 全分辨率 blur bloom 成本高
- DOM 采样和矩阵重建容易造成卡顿
- 高质量模式下点阵密度与流畅度存在明显冲突
- bloom 早期版本不够像荧光，更像普通浅蓝网格

这些问题推动项目进入 WebGL2 升级。

## 5. 第四阶段：WebGL2 GPU 管线升级

为了更充分利用 GPU，项目升级为 GPU 优先架构：

- WebGL2 作为主路径
- Canvas 2D 作为 fallback
- 公共 API 保持不变

新增模块：

- `phosphor/renderer/webgl/gl-utils.js`
- `phosphor/renderer/webgl/shader-sources.js`
- `phosphor/renderer/webgl/webgl-pipeline.js`

### 保留的公共 API

```js
const renderer = new PhosphorRenderer({
  target,
  mount,
  backend: "auto"
});

renderer.start();
renderer.stop();
renderer.updateConfig(config);
renderer.setQuality("high");
renderer.destroy();
renderer.getState();
```

`backend: "auto"` 会优先使用 WebGL2。如果 WebGL2 不可用，则回退到 Canvas 2D。

### WebGL2 管线

WebGL2 主路径为：

```text
Visual Source
→ Source Texture
→ Matrix Quantization Pass
→ Phosphor Emission Pass
→ Bloom Downsample / Upsample Passes
→ Lens Diffusion Compose Pass
→ Display Texture / Noise / Vignette
→ Final Canvas
```

其中：

- 矩阵量化在 shader 中完成
- 发光核心在 shader 中完成
- bloom 在 GPU framebuffer 中完成
- 镜头扩散、暗角、噪声和最终合成都在 shader 中完成

这比 Canvas 2D 更符合实施规格中“WebGL 作为高保真主路径”的判断。

### 为什么仍然需要 CPU source sampling

一个重要限制是：普通网页中的 JavaScript 无法直接读取浏览器已经合成好的视口 framebuffer。

也就是说，WebGL canvas 不能直接“采样它背后的 DOM”。浏览器不会把完整页面合成结果暴露给页面脚本，否则会带来严重安全风险，例如读取跨域 iframe、图片、视频或敏感表单内容。

因此，本项目仍然需要一个 source texture 生成阶段。当前使用自定义 `SourceSampler` 在 CPU 侧近似重建可见页面内容，再把结果上传为 WebGL texture。上传之后的矩阵、发光、bloom 和合成才进入 GPU。

这是当前普通网页环境下的关键边界。

## 6. 第五阶段：性能优化

WebGL2 升级后，卡顿主要不再来自矩阵和 bloom，而是来自 source texture 生成。

因此后续优化集中在两个方向：

1. 最终画面使用 GPU 高频合成
2. source texture 低频、低分辨率更新

### 当前质量档位

当前配置为：

| 质量 | 帧率目标 | source 更新间隔 | sourceScale | 矩阵间距 |
| --- | --- | --- | --- | --- |
| low | 30fps | 720ms | 0.42 | 10 |
| medium | 45fps | 520ms | 0.55 | 8 |
| high | 60fps | 420ms | 0.66 | 5 |

这样做的含义是：

- GPU 每秒可以合成更多帧
- source texture 不会每帧重建
- 高质量模式保留更密的矩阵
- 页面静止时视觉更顺
- 页面变化时 source 会以较低频率刷新

### 关键优化点

- WebGL2 路径关闭 `preserveDrawingBuffer`
- WebGL source texture 降采样
- bloom 使用较低分辨率 framebuffer
- Canvas 2D fallback 保留但不作为主路径
- 控制项仍可调节 `quality`、`matrixPitch`、`bloomStrength`、`noiseAmount`

### 验证结果

真实 Chrome 验证中：

- WebGL2 backend 可正确启用
- Canvas2D fallback 可正确运行
- Console 无错误
- 覆盖层保持 `aria-hidden="true"`
- 覆盖层保持 `pointer-events: none`
- 高质量模式下 `matrixPitch` 为 5，点阵更密
- source frame 在 high 模式下降采样到约 0.66 倍
- 最大 RAF 间隔较早期版本明显下降

## 9. 项目优点

### 视觉方向清晰

项目一开始就通过视觉规范锁定了目标，避免了泛化成常见复古滤镜。冷蓝白磷光矩阵、单元级发光、高光穿透矩阵这些要求都很明确。

### 架构分层较干净

渲染器没有嵌入 `index.html`。测试页只负责初始化和调参，核心逻辑集中在 `phosphor/renderer` 中。

### 可访问性策略正确

DOM 没有被 canvas 替代。视觉层是 `aria-hidden` 的覆盖层，并且不拦截鼠标事件。页面仍保留真实文本、表单、按钮和视频控制。

### GPU 路径已经建立

WebGL2 已成为主路径。矩阵量化、发光、bloom、扩散和合成都在 GPU 中完成，Canvas 2D 只作为 fallback。

### 可渐进调优

质量档位、矩阵间距、bloom、噪声和 backend 都可以继续扩展。当前结构支持进一步加入 html2canvas source、tab capture source 或其他 source provider。

### 适合作为视觉验证平台

测试页本身包含文本、表格、图片、SVG、Canvas、Chart.js、视频和表单。它比单一 demo 更能暴露滤镜在真实网页内容上的问题。

## 10. 项目缺点与限制

### 不能直接读取浏览器视口像素

这是最大限制。普通网页无法像照片编辑软件那样对“整个浏览器已经合成好的画面”直接套自定义 shader。

WebGL 只能处理它自己的 texture。DOM 必须先被采样或重建为 source texture。

### source texture 仍是性能瓶颈

虽然后处理已经 GPU 化，但 source texture 的生成仍在 CPU 侧。页面越复杂，DOM 遍历、样式读取、文本绘制和媒体绘制成本越高。

当前通过 `sourceScale` 和低频刷新缓解了问题，但没有从根本上消除。

### SourceSampler 不是浏览器真实截图

当前 source sampling 是近似重建，不是像素级真实网页截图。因此它对复杂 CSS、阴影、渐变、真实排版、视频细节和第三方内容的还原有限。

### html2canvas 不是实时解决方案

html2canvas 可以提供更真实的 DOM 截图，但它本身也依赖 CPU 侧 DOM 克隆、样式解析和绘制。它适合低频高保真 capture，不适合每帧实时滤镜。

### 高质量与流畅度仍有张力

更密矩阵、更高 DPR、更大 bloom 半径都会提高 GPU 和 source 更新成本。当前 high 模式更适合视觉验证，不一定适合低端设备长时间运行。

### 无法处理所有跨域资源

跨域图片、视频和被污染的 canvas 仍受浏览器安全限制。没有代理或授权时，不能保证完整采样。

### 不是产品级截图/录屏方案

如果目标变成真正的全页面实时视觉转换，普通网页环境不是最理想载体。Chrome extension、Electron、原生壳或屏幕捕获权限会更接近“视口级后处理”。

## 11. 关于 html2canvas 的判断

html2canvas 可以作为后续 source provider，但不应取代当前实时路径。

推荐用法是 hybrid：

```text
快速路径：
  自定义 SourceSampler
  低分辨率、低频率、实时反馈

高保真路径：
  html2canvas
  页面静止后、滚动停止后、手动刷新时运行

GPU 路径：
  始终使用最新 source texture 做矩阵、发光、bloom 和合成
```

这样既能保留当前流畅性，也能在页面静止时得到更真实的 source texture。

不建议：

```text
每帧 html2canvas
→ WebGL
```

这通常会比当前 SourceSampler 更卡。

## 12. 关于“视口级 shader”的判断

用户曾提出是否可以像照片编辑一样，在整个浏览器视口上覆盖一层 shader，直接处理穿过视口的画面。

结论是：普通网页中不能真正做到。

原因是浏览器不暴露页面 compositor framebuffer 给网页脚本。WebGL canvas 无法读取它背后的 DOM、图片、视频和 iframe 像素。这是安全边界。

接近方案包括：

- 浏览器扩展的 tab capture
- Electron 或原生壳
- `getDisplayMedia`
- Chrome extension 的 capture API

这些方案可以把页面或屏幕捕获成 video stream，再作为 WebGL texture 处理。但它们需要权限、存在延迟，也超出普通 HTML 页面范围。

## 13. 后续改进建议

### 增加 source provider 抽象

当前可以把 source 生成进一步抽象为：

```text
SourceProvider
├── FastDomSourceProvider
├── Html2CanvasSourceProvider
├── StaticImageSourceProvider
└── CaptureStreamSourceProvider
```

这样后续可以自由切换 source 来源，而不用改 WebGL 后处理管线。

### 增加 hybrid source 模式

建议新增：

- `sourceMode: "fast" | "accurate" | "hybrid"`
- `html2canvasScale`
- `html2canvasRefreshDelay`

hybrid 模式中，快速 source 先显示，空闲时由 html2canvas 刷新高保真 source。

### 增加可视化调参面板

当前 demo 控件较少。后续可以加入：

- sourceScale
- sourceFrameInterval
- frameRate
- cellFillRatio
- threshold
- contrast
- coreIntensity
- diffusionStrength
- vignetteStrength

这样更适合视觉验证。

### 增加截图对比基准

可以保存几组固定 viewport 截图，用于比较：

- Canvas2D fallback
- WebGL2 medium
- WebGL2 high
- 不同 sourceScale
- 不同 matrixPitch

### 增加暂停 source 更新模式

视觉验证时，很多时候页面是静态的。可以提供：

```text
Freeze Source
```

按钮，用最新 source texture 冻结输入，只让 GPU 后处理继续运行。这样能显著减少卡顿。

### 增加扩展/Electron 方向实验

如果未来目标变为真正的视口级滤镜，可以单独开实验：

```text
tab capture / screen capture
→ video texture
→ WebGL phosphor shader
```

这会更接近照片编辑式后处理，但不再是普通网页内置效果。

## 14. 总结

本项目完成了一次完整的视觉验证流程：

1. 从参考图反推视觉语言
2. 输出视觉规范
3. 输出实施规格
4. 建立 Canvas 2D 原型
5. 暴露性能与视觉问题
6. 升级为 WebGL2 GPU 主路径
7. 保留 Canvas 2D fallback
8. 增加质量档位与参数控制
9. 通过真实 Chrome 验证
10. 明确普通网页环境的边界

当前结果已经证明：冷蓝白磷光矩阵视觉可以在普通网页中实现，并且可以通过 WebGL2 获得比 Canvas 2D 更合理的性能。

但它也证明了另一个现实：普通网页无法直接对浏览器最终合成视口做任意 shader 后处理。真正的瓶颈不是 GPU 能不能做矩阵和 bloom，而是 source texture 如何获得。

因此，本项目当前最合适的定位是：

用于视觉验证的 WebGL2 磷光矩阵滤镜原型。

若继续推进，最佳方向不是继续堆更多 glow，而是完善 source provider、hybrid capture 和性能调参工具。
