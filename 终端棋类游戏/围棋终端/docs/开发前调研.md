# 围棋终端开发前调研

## 状态

- 状态：Draft
- 日期：2026-08-12
- 范围：规则引擎、棋谱/SGF、对局 AI、确定性复现、静态部署可行性
- 非范围：具体视觉特效方案、最终 UI 布局、完整游戏代码

## 目标约束

围棋项目应该继续沿用“终端不是皮肤，而是渲染模型”的原则：画布只负责稳定缩放和字体绘制，棋盘、棋子、星位、气、提子、涟漪、右侧面板都应该先进入字符缓冲区或 Braille 子像素层，再统一绘制。

实现上优先满足：

- 纯本地静态文件可运行，允许 `start.bat` 启本地 HTTP，但不依赖后端服务。
- 规则状态和渲染状态分离，规则层使用 `goban-engine`，项目 wrapper 输出“落子、提子、禁着、终局、得分”等事件。
- 对局过程可复现：同一模式、同一种子、同一 AI 配置，应能复现同一局。
- 第一版 AI 以观赏节奏和视觉可读性为主，不追求强棋力。

- [`goban-engine`](https://www.npmjs.com/package/goban-engine) npm / [Online-Go GobanEngine docs](https://docs.online-go.com/goban/classes/GobanEngine.html)：无显示组件的 Go logic engine。

## 规则引擎候选

### `@sabaki/go-board`

- 定位：轻量 Go board data type。
- 包状态：npm `1.4.3`，MIT，包体约 40 KB，最后修改时间为 2022-04-06。
- 能力：支持棋盘状态、落子、提子、气、连通块、简单 ko、禁自杀、坐标解析等。
- 优点：小、纯逻辑、容易包进静态项目；非常适合我们用自己的终端渲染层。
- 风险：不是完整“比赛规则引擎”，需要自己补 pass、终局、数子/数目、超级劫、贴目、胜负文本和测试。
- 建议：不作为第一版规则核心，保留为轻量 fallback 或测试对照。

### `goban-engine`

- 定位：Online-Go `goban` 项目拆出的逻辑引擎包。
- 包状态：npm `8.3.226`，Apache-2.0，包体约 963 KB，最后修改时间为 2026-02-27。
- 能力：无显示组件，专注 Go game logic，适合 Node 或服务端环境；浏览器静态端需要进一步验证打包方式。
- 优点：维护较新，规则语义可能比小库更完整。
- 风险：接口和依赖面更大；其生态原本服务 Online-Go 的完整应用，不一定适合我们“轻终端观赏局”的简洁架构。
- 建议：已选为第一版规则核心。下一步需要做最小 spike，验证 ESM/静态打包、浏览器运行、棋盘尺寸、规则配置和 move event 提取。

### `jgoboard`

- 定位：模块化 Go 工具箱，包含 board state、rules engine、variation tree、SGF IO、renderer、player。
- 包状态：npm `5.0.4`，CC-BY-NC-4.0，包体约 3.7 MB，最后修改时间为 2026-02-12。
- 优点：功能覆盖面很完整，静态 CDN/ESM 用法清楚。
- 风险：非商业许可；自带 renderer/player 与我们的终端渲染目标重叠。
- 建议：不作为默认依赖；可参考规则 API 和 SGF 思路。

### `goban`

- 定位：Online-Go 的完整 goban 包。
- 包状态：npm `8.3.226`，Apache-2.0，包体约 11.6 MB，最后修改时间为 2026-02-27。
- 优点：功能丰富、活跃。
- 风险：大包和 UI/网络生态耦合概率较高；对我们来说过重。
- 建议：不作为第一版依赖，可保留为以后“更完整围棋客户端”路线的参考。

### `@reis/seki`

- 定位：现代 JavaScript Go board renderer/player。
- 包状态：npm `4.1.0`，MIT，包体约 420 KB，最后修改时间为 2026-08-11。
- 优点：维护非常新，播放器/SGF 展示方向可能有参考价值。
- 风险：主要价值在渲染/播放器，而我们不能直接套普通棋盘 UI。
- 建议：只作为棋谱播放器体验参考，不作为规则核心。

### `tenuki` / `weiqi`

- `tenuki`：web-based Go/baduk/weiqi board library，npm `0.3.1`，MIT，包体约 5.4 MB，较旧。
- `weiqi`：围棋实现，npm `1.0.0`，ISC，依赖 immutable，较旧。
- 建议：都不作为第一版核心。可以在需要补规则测试样例时临时对照。

## SGF / 棋谱

建议第一版就预留 SGF 边界，但不急着做完整编辑器。

- 记录格式：内部使用结构化 move log：`{ color, vertex, pass, captures, boardHash, reason }`。
- 导出格式：后续接 `@sabaki/sgf`，该包 npm `3.5.0`，MIT，最后修改时间为 2026-07-07。
- 用途：回放、测试复现、分享种子、导出 AI 对局。
- 注意：SGF 的规则集、贴目、棋盘尺寸、让子、结果字段应在对局配置里集中维护。

## AI 候选

### Seeded Heuristic AI

- 方式：遍历合法点，按提子、打吃、逃气、连接、断点、边角价值、影响力、眼形风险等打分，再加入 seeded noise。
- 优点：完全静态、快、可复现、易调风格；能刻意控制“像 AI 在下棋”而不是随机乱落。
- 风险：棋力弱；需要避免明显自杀式坏棋和无意义填眼。
- 建议：第一版主力。可以做多名 AI persona，例如 `Influence`, `Territory`, `Capture`, `Balanced`, `Chaos`，它们共享规则和 RNG，只改变权重。

### Seeded MCTS / UCT AI

- 方式：基于合法落子做有限 playout，使用 seeded RNG 控制模拟，限制每步模拟次数或时间。
- 优点：比纯 heuristic 更像在搜索；9x9 上可接受。
- 风险：19x19 成本高；随机 rollout 很容易下得奇怪；可复现需要严格控制迭代次数，不能用真实时间预算。
- 建议：作为第二个内置 AI 来源，先限 9x9/13x13 或低模拟次数。Deterministic 模式用固定 playout 数，Live 模式可用时间预算。

### Pattern Book / Opening Book

- 方式：内置少量定式/布局模板和热力图，前若干手按 seed 选择。
- 优点：开局观感立即改善，棋盘不会出现太多离谱起手。
- 风险：内容需要整理；19x19 模板和 9x9 模板不能混用。
- 建议：配合 heuristic 使用，作为“开局人格”而不是独立 AI。

### KataGo 类强引擎

- 方式：KataGo 原生是强围棋引擎；浏览器内需要 WASM/WebGPU/ONNX Runtime 等适配。
- 已发现候选：`@multi-game-engines/adapter-katago`，npm `1.0.4`，MIT，依赖 `onnxruntime-web`，描述为 KataGo WASM/WebGPU adapter。
- 优点：如果跑通，棋力和观赏性远超自研 heuristic。
- 风险：模型文件、初始化耗时、浏览器兼容、显存/内存、确定性和静态打包都需要专项验证；还可能明显增加项目体积。
- 建议：不要阻塞第一版。后续可以单独开 `engines/katago-experiment/` 探针，先验证 9x9 一步输出耗时和离线资源体积。

### GNU Go / Pachi / Leela Zero

- 方式：传统围棋引擎多为原生程序或 GTP 引擎。
- 优点：理论上可通过 Emscripten 编译成 WASM，或用本地进程驱动。
- 风险：纯静态浏览器运行需要额外编译和适配；本地进程不符合“打开网页即运行”的项目基线。
- 建议：暂不作为第一版依赖。除非后续接受“本地服务 + 网页前端”的模式。

## 推荐第一版技术路线

### 规则层

使用 `goban-engine` 作为唯一权威规则引擎，项目内只做适配层：

- 支持棋盘尺寸：9、13、19。
- 默认规则：优先使用 `goban-engine` 能稳定支持的规则配置；如果 Chinese/Japanese scoring 都可用，再按视觉对局需求选择。
- 适配层职责：初始化棋局、提交 AI 落子/pass、读取提子/禁着/终局/得分、生成 move log、把规则事件转成终端动画事件。
- 禁止重复实现：不要在渲染层重写提子、劫、禁自杀等核心规则，只能读取规则层结果。
- 自动终局：优先使用引擎状态；如果需要观赏局保护，可在 wrapper 增加最大手数或连续 pass 守卫。

### AI 层

定义统一接口：

```js
async function chooseMove(position, player, rng, budget) {
  return {
    color: "black",
    vertex: [x, y],
    pass: false,
    score: 12.4,
    reason: "capture-threat"
  };
}
```

内置 AI 分两级：

- `heuristic-*`：确定性、快、适合所有尺寸。
- `mcts-*`：固定 playout 数，先对 9x9/13x13 启用。

### 模式

延续国际象棋项目的经验，围棋也建议拆两种模式：

- Deterministic / Replay Mode：所有 RNG seeded，固定 AI 选择、固定迭代次数、固定超时判负逻辑。
- Full Engine / Live Mode：允许真实时间预算和更自然的不确定性；种子只作为开局/配对/视觉标识，不承诺完全复现。

### Worker 边界

AI 一律放在 Web Worker 或可替换的异步层里：

- 主线程只处理终端渲染和动画。
- 每步 AI 设置硬超时，超时记为 timeout loss 或 forced pass。
- 强引擎如果接入，worker 必须复用，不能每步重建。

## 测试准备

第一版至少准备这些测试：

- 合法落子：提子、禁自杀、简单劫、pass。
- 终局：双方连续 pass、最大手数、防无限循环。
- 确定性：同一种子、同配置连续跑多局，move log 完全一致。
- AI 超时：模拟 AI 不返回，10 秒或配置时间内判负/中止。
- 渲染约束：棋子/特效只通过字符缓冲区输出，不直接画自由粒子。

## 特效讨论前置问题

等进入视觉讨论时，建议先决定这几件事：

- 棋盘是 19x19 细线交点，还是终端字符里的“点阵网格场”？
- 棋子是实心 Braille 圆、字符阴影圆，还是类似中国象棋的圆形棋子但去掉汉字？
- 提子效果是“棋子被气流抽走”，还是“连通块像墨滴一样消散”？
- 气/liberty 是否可被视觉化，例如濒死棋链周围出现低亮度呼吸点？
- 胜负/终局是否要用整盘字符波纹定格，还是只在右侧 panel 做结果提示？

我的倾向是：围棋不要照搬象棋的“棋子移动拖尾”。围棋最有味道的是落子、气、提子和地盘，所以特效应该围绕“交点被点亮”“气脉收缩/扩张”“被提棋块消散”来做。
